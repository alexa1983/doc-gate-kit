# doc-gate-kit —— 文档层闸门（可复用套件）

一个**跨项目共用**的文档检查套件：判据只维护一份，新项目只放一个基线和 4 行 workflow。

只判两条**与业务无关**的规则：

| 判据 | 判什么 | 为什么值得占一个 CI 位 |
|---|---|---|
| **死链** | Markdown 里 `[文字](相对路径)` 的目标在不在 | 路径写错、文件被挪、链接指到不入库的生成物——这三类靠人眼查不出来 |
| **编码** | 非法 UTF-8／`U+FFFD`／异常控制字符 | 中文被静默截断的文件能通过 `git`、`cat`、`file`，肉眼也看不出，打开才炸，且**不可逆** |

**刻意不判**：编号体例、模板节数、目录表规矩、接口与字段是否对齐。那些是**各项目自己的口径**，抄过来只会制造假红——假红会训练人无视红灯。

---

## 一、为什么是"套件 + 薄调用"，而不是每个项目拷一份

**判据只能有一份。** 如果新项目里也放脚本，就会出现本机跑旧判据、CI 跑新判据，结果是
"本地绿、CI 红"——**那比不装更坏，因为你会开始不信红灯**。

所以本套件的分工是：

| 放什么 | 放哪 | 每项目各一份？ |
|---|---|---|
| 3 个检查脚本 | **只在本仓库** | ❌ |
| `bin/dg` 入口 ＋ skill | **只在本仓库**（skill 靠软链挂到 `~/.dsh/skills`） | ❌ |
| `扫描目录` ＋ 基线读数 | 各项目的 `03_项目工具/闸门基线.json` | ✅ |
| 4 行 workflow | 各项目 `.github/workflows/docs.yml` | ✅ |
| 薄 pre-commit 钩子 | 各项目钩子目录（调本仓库） | ✅（不入 git，需重装） |

升级判据 = 改本仓库一次，所有项目下次 push 自动跟上。

## 二、装进新项目：一条命令

```sh
cd ~/work/新项目          # 必须在 git 仓库里（worktree 也行）
sh ~/tools/doc-gate-kit/install.sh            # 自动探测
sh ~/tools/doc-gate-kit/install.sh docs 方案   # 或显式指定要扫的目录/文件
sh ~/tools/doc-gate-kit/install.sh --hook-only # 只装提交钩子（其余已有）
```

它会做七件事，**一件都不覆盖你已有的文件**：

1. 写 `03_项目工具/闸门基线.json`（只登记扫描清单，读数留空）
2. 写 `.github/workflows/docs.yml`（4 行，显式带 `kit-repository`）
3. 装薄 `pre-commit` 钩子（已有钩子时**只警告、不覆盖**；设了 `core.hooksPath` 就装到那里）
4. 把 `03_项目工具/生成物/` 写进 `.gitignore`（报告是可重跑的产物，不是事实源）
5. **跑尺子自检**：9 项坏样本，见第五节
6. 空跑一次，把现有问题逐条列出来
7. **不落基线**，把定性权留给人

**扫描清单怎么来的**：自动探测 `docs/文档/方案/文档中心`，**并把根目录的 Markdown 一并登记**。
2026-10-18 之前只登记目录，于是"根 README 有死链、装了钩子却全绿"——最隐蔽的一种假绿
（实测：`docs/` 里 1 份、根 README 有 1 条死链，空跑报"0 份 Markdown、0 条链接"）。
`扫描目录` 里允许写**具体文件**，不只目录（目录与其下的文件同时登记时会自动去重）。

### 装完必须做：落基线（这一步不能省）

第一次空跑一定会报出历史旧账。**不要 `--update-baseline` 一把拍平**——那等于把旧账埋了。
正确顺序：

1. 看明细，逐条定性：**真该修**就修；确实是"本机才有、不入库的素材"
   （且路径已被 `.gitignore` 覆盖）本来就不会计入；
2. 定性完再落基线，并把每条 `登记` 改成"谁、什么时候、接受了什么"：

```sh
node ~/tools/doc-gate-kit/run_docs_gate.mjs --root "$(pwd)" --update-baseline
```

`--update-baseline` 只改本套件认识的两个读数，**基线里的其他条目、其他指标、`登记` 与 `备注` 全部原样保留**
（2026-10-18 修：此前会重建整个 `条目`，把别的判据连同"谁接受了什么"一起抹掉——实测 4 条基线跑完只剩 2 条）。

## 三、一条命令：dg（推荐入口）

`bin/dg` 把"新建就装上"收敛成一个动作，**AI 与人走同一条路**：

```sh
KIT=$(cd -P ~/.dsh/skills/doc-gate/../.. && pwd)   # 或直接写套件目录
sh "$KIT/bin/dg" new ~/work/新项目     # 新项目：git init → README → 装闸门 → 验证 → 首次提交
sh "$KIT/bin/dg" adopt ~/work/老项目    # 老项目：只装钩子与 CI，**基线不落**
sh "$KIT/bin/dg" check .                # 只跑不装，退出码同闸门（0／1／2）
sh "$KIT/bin/dg" self-test              # 拿临时仓库验上面三条路，不动真实项目
```

想直接敲 `dg`（不用每次写全路径）：`ln -sfn "$KIT/bin/dg" ~/.local/bin/dg`（`~/.local/bin` 需在 PATH 里）。

**新与老的分界，就是"能不能自动落基线"**：

| | 新项目（空目录／刚 init） | 老项目（已有文档） |
|---|---|---|
| 基线 | **自动落 0** | **不落**，人逐条定性后再落 |
| 为什么 | 没有旧账，0 就是真 0，全自动是安全的 | 自动落＝把旧账埋了，以后"变红"和"本来就红"分不出来 |

`dg new` 会**拒绝非空目录**——这不是啰嗦：把老项目当新项目装，等于一次性拍平历史旧账。

### 目录里已经有东西了，怎么办

就一条：`dg adopt`。它和 `new` 的区别只有"落不落基线"，其余步骤一样。

| 你手里的情况 | `dg adopt .` 会做 |
|---|---|
| 有文档／有代码，**已是 git 仓库** | 装钩子、workflow、基线（0），然后列出历史旧账 |
| 有文档／有代码，**还没有 .git** | 先 `git init`（只建 `.git`，不动你的文件），再同上 |
| 你站在**仓库的子目录**里 | 装到**仓库根**（钩子与 workflow 必须是仓库级的），并提示你一声 |
| 已经有**自己的闸门**（基线里有别的判据） | 会先警告"两套闸门会并存"，不替你合并 |
| 已有 `.github/workflows/docs.yml` 或 pre-commit 钩子 | **不覆盖**，只打印要手工加的那一行 |

装完不是结束——`adopt` 刻意不落基线，它会打出"逐条定性 → 再 `--update-baseline`"的下一步。
**这一步不能省**，理由同上：老项目的 0 不是真 0。

### 给 AI 用的 skill

`skills/doc-gate/SKILL.md` 随套件走；DSH 扫 `~/.dsh/skills`，本机用软链挂上（改 skill 即改套件，不漂）：

```sh
ln -sfn "<套件根>/skills/doc-gate" ~/.dsh/skills/doc-gate
```

skill 只写**决策**——新／老怎么分、落基线前怎么定性、三条禁令——**判据一律指回套件**。
在 skill 里再写一份判据，就回到"两份判据、本地绿 CI 红"的老路了。

**它的边界照实写**：skill 只在"经由 DSH 的会话"里被调用，靠措辞命中；终端里手搓 `git init`、
别的机器、别人建的项目，它都管不到。所以它是**提醒层**——"一定装上"靠 `dg` 这条入口，
"装上之后别悄悄坏"靠 CI。

## 四、退出码三档（调用方要区别对待）

| 码 | 含义 | CI 里 | pre-commit 里 |
|---|---|---|---|
| **0** | 不比基线差 | 绿 | 放行 |
| **1** | 比基线差（真的新增了缺陷） | **红** | **拦住** |
| **2** | **闸门自己跑不成**（配置缺／目录不存在／一份 Markdown 都没读到／脚本异常） | **红**（"闸门坏了"必须有人管） | **放行**（fail-open，守卫坏了不能挡住干活） |

`2` 在两边处理不同，是刻意的：**"没查成"既不等于"通过"，也不该拦人干活**。
钩子里遇到 2 会放行，但 CI 里 2 必须是红——否则闸门某天静默失效，没人知道。

**"扫了 0 份"一律走 2，不许绿**。2026-10-18 之前只挡了"`扫描目录` 是空数组"，
于是目录名写错、目录为空、`--hook-only` 被误当成目录，都会得到一份体面的全绿报告。
现在这三种全部退 2 并点名是哪个路径不存在。

### 两种模式：全量 与 `--staged`

| 模式 | 谁用 | 死链看哪 | 编码看哪 | 判据 |
|---|---|---|---|---|
| 默认（全量） | CI | 工作区 | 工作区 | 比基线 |
| `--staged` | pre-commit | 工作区 | **暂存区** | 编码**绝对为 0**（不参与基线） |

不能互换。**工作区干净不代表索引干净**：`git add -p`、或"改完忘了重新 add"，都会让
工作区干净而索引里留着坏字节——实测那条路能带着非法 UTF-8 提交成功。
钩子只该管"这次提交"，存量坏文件由 CI 的全量扫描管。

## 五、怎么验这套东西真的有用（只验绿等于没验）

| 做坏什么 | 期望 |
|---|---|
| 写一个指向不存在文件的链接 | 退出 1，明细点名那一行 |
| 往文本文件塞非法 UTF-8 字节 | 退出 1，报"不是合法 UTF-8" |
| 撤掉上面两处 | 退出 0 |
| 把链接写进围栏代码块（``` 里）当示例 | 退出 0（示例不是链接） |
| 一条链接往仓库根之上爬（`../../外面.md`），同时另一条指向 `.gitignore` 忽略的本机素材 | 只报越界那条，**豁免那条仍豁免** |
| 把 `扫描目录` 改成空数组／写一个不存在的目录 | 退出 **2**（"没东西可查"不许绿） |
| 删掉基线文件 | 退出 **2** |
| 基线里有别的判据条目，跑 `--update-baseline` | 那些条目**原样保留** |
| 暂存坏字节、再把工作区改干净，然后提交 | 钩子退 **1**（看索引，不看工作区） |
| 让链接指向 `.gitignore` 忽略的文件、再删掉那个文件（模拟干净检出） | 仍退出 **0** |

随时可跑内置自检（不动项目文件）：

```sh
node ~/tools/doc-gate-kit/run_docs_gate.mjs --self-test
```

自检本身就是上面那张表的实现，**9 项**：干净样本判 0（含目录/文件重复登记去重）、坏链接报出、非法 UTF-8 报出、
代码块示例不误报、越界链接不毒化豁免、以两点开头的文件名不算越界（⑤b）、缺目录退 2、更新基线保留未知条目、暂存区坏字节退 1。
**任何一项失败就不许把它当闸门用**。

## 六、三个踩过的坑（都已修，都是"绿灯其实没在判"）

### 坑 1：`git check-ignore` 会转义中文路径（2026-10-18，CI 上撞出来）

`git check-ignore` 输出中文／非 ASCII 路径时默认 **C 转义并加双引号**
（`"04_\347\224\237..."`）。直接拿它的 stdout 建集合，会与原始中文路径
**永远匹配不上**，那条"被 `.gitignore` 忽略就不算死链"的豁免会**静默失效**：

- **本机看不出来**（被忽略的文件都在盘上，只有"目标缺失"那一支才走这个判断）；
- **一进 CI 就炸**（干净检出里它们必然缺，于是几十处环境必然被报成硬缺陷）。

修法是改用 `-z --stdin`：输入输出都是 NUL 分隔的原样字节，转义问题从根上没有了。
（`-c core.quotePath=false` 也一并留着，双保险。）

### 坑 2：一条越界路径会毒化整批查询（2026-10-18 复查发现）

链接往仓库根之上爬、解析成 `../xxx` 时，`git check-ignore` 直接
`fatal: ... is outside repository` 并以 **128** 退出。旧代码把这当成"git 不可用"，
于是**全部缺失一律按硬死链计**，整个豁免归零——**同一个"假红"从另一个门口又进来一次**。

实测（一个 489 份 Markdown／2.1 万条链接的真实仓库）：修前把 1742 条
"本机素材、干净检出必缺"全部算成硬死链，报出 2892 处；修后这 1742 条正确豁免。

修法两层：**先剔除越界路径**（仓库外的东西按定义不可能被 `.gitignore` 忽略），
**再分块查询＋二分降级**（单块里万一还有坏路径，只影响那一条，不再拖垮全局）。

### 坑 3：提交钩子看工作区、不看索引（2026-10-18 复查发现）

编码守卫一开始扫的是磁盘文件。把坏字节 `git add` 进索引、再把工作区改回干净，
**提交成功，坏字节进了提交**——而它的卖点恰恰是"提交那一刻拦住"。
修法是钩子带 `--staged`，用 `git diff --cached` 列文件、`git cat-file blob` 读**暂存区内容**再判。

**这三件事本身就是这套东西存在的理由：闸门装了、报表是绿的，不等于它真的在判。**

## 七、三层"自动"的真实边界（实测，不要相信"全自动"）

| 要内置的东西 | 能真自动吗 | 机制 | 硬限制 |
|---|---|---|---|
| 提交时检查 | ✅ 装一次管所有仓库 | 钩子目录（含 `core.hooksPath`） | **只在这台机器**；钩子里没有 `node`／不在仓库里就 fail-open |
| push 时检查 | ⚠️ 半自动 | reusable workflow（本项目 4 行） | 仍要有人写那 4 行；套件仓库要可见 |
| 脚本文件本身 | ❌ 不能 | 必须在某个仓库里 | CI 只认仓库里的文件 |

实测两条结论：

- `git init --template` 只会把文件拷到 `.git/` 里，**不进工作区**，且 **`clone` 完全不用模板**；
- 项目里设了 `core.hooksPath` 时，全局钩子**不生效**（项目级优先）——所以"全局兜底"和"项目自带"不能同时成立。

**真正能跨机器保证的只有 CI。** 本机那一层一律是"尽力而为"，别把它当保证。

## 八、升级与维护

- 判据改了 → 只改本仓库，所有项目自动跟上（这也意味着**一次改错会影响所有项目**，
  所以本仓库自己也要有 CI，且每次改完先跑 `--self-test`）。
- 套件**改名／fork／换账号** → 调用方的 `kit-repository:` 要跟着改（显式写了才不会 404）。
  `install.sh` 会从套件的 git remote 推断，写进生成的 workflow。
- 套件目录**移动到别处** → 各项目的薄钩子里写的是绝对路径，会失效。
  重跑 `install.sh --hook-only` 会提示已有钩子、不覆盖；需要手工改钩子里的 `KIT=` 那一行。
- **不要把本套件的脚本拷进被检查的项目**——那就回到"两份判据"的老路了。

## 九、已知局限（照实写）

1. **判不了语义**：比如"代码读错了同名列"这种错，两边的列都在、文档也都写了，结构比对报不出来；
2. **只判 Markdown**：`.vue`／`.py` 里的路径错误不在射程内；引用式链接（`[x][id]`）也**不查**；
3. **不查锚点**：`[x](a.md#某章节)` 只看 `a.md` 在不在，不看 `#某章节` 是否存在；
4. **站点绝对路径不判**：`/docs/x.md`、`//cdn/x` 被计入"跳过"数并打印，因为无法判断站点根在哪；
5. **编码判据会误报二进制伪装成文本**：若把 `.svg`／`.json` 当文本写了二进制内容，会报非法 UTF-8——这是对的，但值得知道；
6. **`--staged` 只判本次提交**：本次没动到的存量坏文件不会被钩子发现，靠 CI 的全量扫描兜；
7. **不覆盖已有钩子**：项目里已有 `pre-commit` 时不覆盖，只打印要手工加的那一行；
8. **"问不到 git"的路径是保守处理、不是精确判定**（2026-10-18 补）：`git check-ignore` 对个别路径会以非 0/1 退出（不在仓库里、路径怪异），这些路径**按"没被忽略"计入硬死链**（宁可多报），但会单列在报告的 `unknown` 里点名。**它不会让豁免整批失效**——这一点由自检 ⑤ 钉住（一条 `../` 越界不能把同批的豁免一起弄丢），自检 ⑤b 另钉住"名字以两点开头的正常文件不算越界"。
